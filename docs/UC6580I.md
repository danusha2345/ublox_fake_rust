# Unicore UC6580I — заметки по протоколу

Документ собран на трёх источниках:

1. **Протокольная спецификация Unicore**: *UFirebird II Series Protocol
   Specification, UC-04-FB2 EN R1.2 (Dec. 2024)* — UC6580 входит в
   эту серию. PDF:
   `https://en.unicore.com/uploads/file/UFirebirdII%20Series%20Protocol%20Specification_EN_R1.2.pdf`
2. **Datasheet**: *UC6580x-00 Dual-Frequency GNSS Positioning Chip
   Datasheet, UC-02-FB2 EN R1.5 (Jun. 2025)* — аппаратная часть, распиновка,
   электрические характеристики, режимы загрузки. PDF:
   `https://en.unicore.com/uploads/file/UC6580x-00_Datasheet_EN_R1.5.pdf`
3. **Собственный raw-анализ** сессий 22 апреля 2026 г. в
   `uart_term` (`target/release/log_2026-04-22_17-27-43.txt` и
   сопутствующие) — с извлечением бинарных RTCM3 / Extended RTCM
   (msg 4074) кадров, верификацией CRC24-Q и разбором каждого
   Sub-ID.

Если поле совпадает с доком — указано «(doc 3.x.x)». Если ничего
нет — значит это **видно в реальных логах, но отсутствует в
публичной версии R1.2**; скорее всего OEM-расширение прошивки
`R6.1.1.1Build9074`, установленной в нашем экземпляре.

## 1. Чип и прошивка

Из ответа `$PDTINFO`:

```
$PDTINFO,UC6580I-00,G1B1L1E1,V00,R6.1.1.1Build9074,2400615000514,20250427080308004*4D
```

| Поле | Значение | Смысл (doc 3.2.1) |
|---|---|---|
| pdtName | `UC6580I-00` | модель / hardware part-number |
| config | `G1B1L1E1` | созвездия поддерживаемые **железно** (не зависит от конфигурации): **G**PS, **B**DS, G**L**ONASS, Gali**l**eo — у каждого флаг «1» = поддерживается |
| hwVer | `V00` | hardware revision |
| fwVer | `R6.1.1.1Build9074` | прошивка |
| PN | `2400615000514` | part number |
| SN | `20250427080308004` | серийный номер (для чипа = chip ID) |
| cs | `4D` | XOR-чек-сумма NMEA |

Синоним с бóльшим составом — `$PRODUCTINFO` (doc 3.2.2), добавляет
поле PTV (protocol version) и 4 reserved. В наших логах **не
вызывалась**, но поддерживается.

**UC6580I** — 96-канальный двухдиапазонный GNSS-приёмник, поддержка
GPS, GLONASS, BDS, Galileo, QZSS, NavIC, SBAS.

## 2. Аппаратная часть

Данные из *UC6580x-00 Dual-Frequency GNSS Positioning Chip Datasheet,
UC-02-FB2 EN R1.5 (Jun 2025)* —
`https://en.unicore.com/uploads/file/UC6580x-00_Datasheet_EN_R1.5.pdf`.

### 2.1 Характеристики (doc 1.2–1.3)

| Параметр | Значение |
|---|---|
| Процесс | 22 nm, SoC (RF + baseband на одном кристалле) |
| Корпус | QFN40, 5 × 5 × 0.85 mm |
| Каналы | 96 |
| Update rate | до 10 Гц |
| Sensitivity | acquisition −148 dBm / tracking −162 dBm |
| Accuracy (horizontal, RMS) | 1.5 m SPP |
| TTFF | 26 с cold / 2 с hot / 1 с reacquisition |
| Потребление | 40 mA @3 V (tracking/acquisition, DCDC) / 5 µA backup |
| Anti-jamming | wideband/narrowband ≥ −75 dBm |
| Форматы | NMEA 0183, Unicore, RTCM 3.x |
| Встроенный Flash | есть (не требуется внешний) |
| Secure boot | есть |

Две модели (doc 10.4):

| Model | Grade | T<sub>op</sub> | Стандарт | MSL |
|---|---|---|---|---|
| UC6580**A**-00 | Automotive | −40…+105 °C | AEC-Q100 G2 | 1 |
| UC6580**I**-00 | Industrial | −40…+85 °C | JESD47 | 3 |

Распиновка у A и I идентична. Наш экземпляр — **I**.

### 2.2 RF-подсистема (doc 4, 7.4)

Входная частота 1166…1620 МГц, один SAW + LNA + down-conversion,
два параллельных ADC (I/Q) на каждом из двух диапазонов.

| Вход | Диапазон (typ) | Сигналы |
|---|---|---|
| L1_IN (пин 40) | 1559–1606 МГц (1575.42) | GPS L1, Gal E1, BDS B1I/B1C, GLO G1, QZSS L1, SBAS L1 |
| L5_IN (пин 38) | 1166–1217 МГц (1176.45) | GPS L5/L2, Gal E5a/E5b, BDS B2a/B2I, GLO G2, QZSS L5, NavIC L5 |

Прошивка выбирает одну из двух пар:

| Mode | L1_IN | L5_IN |
|---|---|---|
| 1 | GPS L1 / Gal E1 / BDS B1I/B1C / GLO G1 | GPS **L5** / Gal **E5a** / BDS **B2a** |
| 2 | то же | GPS **L2** / Gal **E5b** / BDS **B2I** / GLO G2 |

Наш `R6.1.1.1Build9074` работает в **Mode 1** — это видно по
`$CFGSYS sysMask = 0x55155` (L1 + L5) и по составу RTCM MSM-кадров.

Рекомендуемый внешний LNA: gain 17–60 dB, мишанровое сопротивление 50 Ω,
SAW-фильтр обязательно в зашумлённой обстановке.

QFN40, 40 пинов. Power:

| Пин | Имя | Назначение |

| 23 | V_CORE | вход питания ядра |
| 24 | LDO_C | выход core-LDO (нужен decoupling-конденсатор) |
| 2 | LDO_X | выход TCXO-LDO (1.8 V или 2.8 V — определяется при production) |
| 5 | LDO_EX | внутренний, decoupling-конденсатор |
| 10 | LDO_RET | выход backup-LDO |
| 6 | V_BACK | backup-питание (RTC + Retention RAM), 1.7–3.6 V |
| 8 | V_DET | antenna-detection (currently not supported) |
| 9 | VDD_ANT | питание активной антенны, 2.7–3.6 V |
| 17 | RESETN | активный низкий, длительность ≥ 5 мс |

| Пин | Имя (PIO) | По умолчанию | Альтернативы |
|---|---|---|---|
| 18 | **RX** (PIO7) | **UART1 RXD** | SPI slave MOSI |
| 19 | **TX** (PIO6) | **UART1 TXD** | SPI slave MISO |
| 31 | SCL (PIO8) | I²C1 SCL | SPI slave CLK |
| 32 | SDA (PIO9) | I²C1 SDA | SPI slave CSN |
| 33 | D_SEL (PIO10) | boot-mode select | PPS, 32.768 kHz out |
| 34 | BOOT_MODE (PIO12) | boot-mode select | PPS, RF_READY, UART1_TXD |
| 35 | PPS (PIO11) | 1PPS out | EVENT in, UART1 RXD |
| 36/37 | PIO15/16 | GPIO | **UART2 TX/RX**, LO1/LO2 detect |
| 25–30 | PIO0–PIO5 | GPIO | SPI master, SPI flash, PWM0/1 |
| 13/14 | PIO14/13 | GPIO | ODO_CNT/DIR, EVENT |
| 15/16 | TCK/TMS | JTAG debug | GPIO, ODO |

Логические уровни: `Vih = 0.8·VDD_IO`, `Vil = 0.2·VDD_IO`,
`Iout = ±5 mA` @ `Vol/Voh = 0.4 / VDD_IO-0.55 V`.

### 2.4 Режимы загрузки (doc 6.2)

В первые **40 мс после power-on / RESETN** ЦПУ детектирует запрос
firmware-upgrade через выбранный интерфейс. Выбор — пинами
`D_SEL` (PIO10) и `BOOT_MODE` (PIO12):

| Mode | D_SEL | BOOT_MODE | Upgrade/boot канал | UART1 на пинах |
|---|---|---|---|---|
| **1** | X | 1 или open | UART1 **и** I²C1 | PIO6/7 (наш случай) |
| 2 | 0 | 1 | UART1 только | PIO11/PIO12 |
| 3 | 0 | 0 | SPI slave | — |

Если за 40 мс запрос не пришёл — грузится из built-in Flash
(он есть у UC6580x всегда), иначе — из внешней SPI-флешки.

Практический вывод: наш модуль прошит в Mode 1, UART1 зафиксирован
на PIO6/PIO7, I²C1 доступен на PIO8/PIO9 (но не используется).
Для flash-upgrade через serial — подать правильный уровень на
`BOOT_MODE` до ресета, затем послать handshake в окно 40 мс.

После `RESETN` `BOOT_MODE` и `D_SEL` становятся обычными GPIO.

### 2.5 Тактирование и сброс (doc 3.3–3.4)

- **TCXO 26 MHz** — обязательный внешний источник тактов на пине
  TCXO_IN. Должен стабилизироваться ≤ 10 мс после подачи питания,
  иначе PLL не стартует. Частота TCXO: точность ≥ 0.5 ppm,
  амплитуда 0.5–1.4 Vpp.
- **RTC 32.768 kHz** — нужен для hot-start и backup-режима.
  Вариант A: внешний кварц на RTC_I/RTC_O (пины 11/12),
  нагрузочная ёмкость 12.5 pF. Вариант B: внешний цифровой сигнал
  0.9–1.98 V на RTC_I. Если hot-start не нужен — RTC_O на GND,
  V_BACK = VDD_IO.
- **RESETN** — активный низкий, длительность ≥ 5 мс. Также есть
  watchdog (2 сторожевых) и soft-reset по команде firmware.

### 2.6 Режимы питания (doc 3.2, 6.1)

Три состояния:

1. **Running** — все домены активны, CPU работает, интерфейсы
   открыты. Потребление ≈ 40 mA @ 3 V.
2. **V_BACK mode** — IO/main отключены, работает только RTC и
   Retention RAM (хранит эфемериды для hot-start). Потребление
   ≈ 5 µA @ 3 V. Пробуждение — по подаче VDD_IO.
3. **Power off** — всё выключено.

Две схемы питания:

- **DC-DC mode** — `DCDC_IN → DCDC_OUT` → дроссель 1 µH → `V_CORE`.
  Наиболее эффективный режим.
- **LDO mode** — `DCDC_IN` соединён с `DCDC_OUT` (внутренний DC-DC
  обойдён), `V_CORE` запитан от LDO_EX. Упрощает схему BOM.

`V_BACK` может быть отдельным источником или объединён с `VDD_IO`.
Если отдельный — нужен диод против обратного тока (V<sub>f</sub> ≤ 300 mV).

## 3. UART-интерфейсы

Модуль имеет до трёх physical-портов: **I²C**, **UART1**, **UART2**,
**SPI**. В командах используется нумерация портов:

| `portID` | Порт |
|---|---|
| 0 | I²C |
| 1 | UART1 |
| 2 | UART2 |
| 4 | SPI |

В нашем стенде:

| В логе | Реально подключён к | Роль |
|---|---|---|
| `ttyUSB0` | UART1 (выход данных) | основной поток: boot-dump, NMEA, RTCM3, extended RTCM (4074), ответы на команды |
| `ttyUSB1` | UART2 (или та же UART1, но TX-линия хоста) | вход команд конфигурации |

Настройка порта — `$CFGPRT` (doc 3.3.1):

```
$CFGPRT,portID,addr,baud,inPro,outPro
   baud  = 9600/14400/19200/38400/57600/115200/230400/460800/921600
   inPro  bit0 = UNICORE ; bit7 = RTCM3.3 ; bit10 = MAPFB+ODODATA (UM621/UM681A)
   outPro bit0 = UNICORE ; bit1 = NMEA ; bit2 = RTCM3.3
          bit5 = Notice ; bit7 = Ext-RTCM 4074_DR (UM621/UM681A)
          bit8 = Ext-RTCM 4074_PVT (UC6580, UM670A, UM680A, UM621)
```

Отключать `inPro.bit0 = UNICORE` нельзя — модуль перестанет
принимать команды и вернёт `FAIL`.

Для нашей конфигурации `outPro` = `bit1 | bit2 | bit8` = `0x106`
(NMEA + RTCM3.3 + Extended RTCM 4074 PVT).

**Наша скорость UART1 = 921600 бод** (определено по раскладке
кадров в логе `log_2026-04-22_17-27-43.txt`: 285 089 байт за 132.57 с
даёт ≈ 21 500 байт/с полезного трафика, что соответствует утилизации
≈ 23 % от 921600 Бод 8N1 — см. §6.6). Это максимальная поддерживаемая
скорость по doc 3.3.1. На 460800 канал был бы уже перегружен по
пиковым всплескам RTCM MSM.

Практическая настройка RP2350/RP2354 для Unicore-прошивки:

- `UART0 TX = GPIO0` должен использовать те же pad-настройки, что и
  рабочая u-blox прошивка: 12 mA drive, pull-down, fast slew.
- `UART1 RX` FIFO interrupt threshold должен быть `1/4` (`rxiflsel=0b001`).

Если мусор виден даже в raw passthrough, сначала проверять эти две
аппаратные настройки и физическую распиновку/землю, а уже потом NMEA/RTCM
роутер. Raw passthrough не парсит поток и потому не может сам превратить
валидный UART в мусор.

## 4. Стартовая последовательность (boot-up)

Документированное стартовое сообщение (doc 1.4) для UM621-02:

```
UM621-02 G1B1L1E1 COM1
PN 2310414000033
SN 000101114303845
HWVer 1.2
FWVer R6.0.0.0Build2810
Copyright (c), Unicore Communications Inc.
All rights reserved.
```

**У нашего UC6580I с прошивкой R6.1.1.1Build9074 формат
отличается** — выдаётся структурированный debug-dump,
которого в публичной доке R1.2 нет.

### 4.1 Полный наблюдаемый boot-dump

Первые ~6.7 КБ сессии (до начала потока `$GN*`), с разбивкой на
логические блоки. Эмулятор хранит этот блок в
`src/unicore/boot_dump.bin` (см. §4.3 для процедуры обновления через
`boot-capture` feature) и при старте Emulation шлёт его одним
`enqueue_chunked(BOOT_DUMP)`:

```
\r\n
UC6580I-00 G1B1L1E1 COM1\r\n
PN 2400615000514\r\n
SN 20250427080308004\r\n
HWVer 00\r\n
FWVer R6.1.1.1Build9074\r\n
Reset Count:0\r\n
Init time:0,0,0,0.000000,ms:0,
          INIT:0,0,0.000000,0.000000,0,
          ms:606631,2217,210679.400463,F,F,6.2
```

| Поле | Пример | Смысл (определено опытно) |
|---|---|---|
| `Reset Count` | `0` | счётчик сбросов с момента last-power-on; инкрементируется watchdog-рестартом |
| `Init time:0,0,0,0.000000,ms:0` | нули | «холодный» маркер (NVM-время не восстановлено) |
| `INIT:0,0,0.000000,0.000000,0` | | start-position NVM (если есть — сюда пишется last-known fix) |
| `ms:606631` | аптайм бутлоадера, мс | время до передачи управления прошивке |
| `2217` | GPS week | номер недели (могло восстановиться из almanac) |
| `210679.400463` | GPS TOW, с | в примере ≈ четверг 00:31:19 UTC |
| `F,F` | флаги «almanac valid / ephemeris valid» | `F` = невалидно, `T` = валидно |
| `6.2` | версия init-партиции (предположительно) | постоянно в наших сессиях |

```
$$$_PVT_INIT_INFO_START_
00000501, 00000000, 00000000, 01002000, 01010101, 01010100,
00010001, 00000096, 00000096, 00000000, 00050000, 00050000,
00000000, 00010001, 000F4240, 0007A120, 00055155, 00055155,
000008F700000000, 00000000, 000000010102, 120100FF, 5A121204, 000000
```

Это dump внутренней структуры PVT engine — 32-битные hex-поля.
Частичная расшифровка (по совпадению с полями `$CFGSYS`):

| Offset в dump | Значение | Предположительно |
|---|---|---|
| 17, 18 | `00055155, 00055155` | `sysMask` (см. `$CFGSYS` ниже) — активная маска созвездий и её «целевое» значение |
| 15, 16 | `000F4240, 0007A120` | `0x000F4240 = 1 000 000` — возможно `MeasRate × 1000`; `0x0007A120 = 500 000` — `NavRate × 1000` |
| 7, 8 | `00000096, 00000096` | `0x96 = 150` — возможно число каналов / decIdx |
| 10, 11 | `00050000, 00050000` | `0x50000 = 327680` — возможно флаги подсистем |

```
$CHCFG,00055155,00055155,0,016,01,10,01,10;1,018,11,22,11,22;
       2,019,23,30,23,30;3,000,31,48,31,48;4,001,49,56,49,56;
       5,131,57,64,57,64;6,002,65,84,65,84;
```

`$CHCFG` — **Channel Configuration dump** (не в публичной доке).
Формат: `$CHCFG,<sysMask>,<sysMask>,<reserved>,<group0>;<group1>;…`
Каждая группа: `<idx>,<sigId>,<chBegin>,<chEnd>,<chBegin>,<chEnd>;`.
По частотам и номерам каналов видно, как модуль делит 96 корреляторов
между сигналами. Полная семантика требует доступа к RTL / OEM-доке.

```
$PTINFOPKG,34,<hex>,<hex>,<hex>,...
```

Partition-Information Package — 34 блока hex-данных, кажется, описывают
разделы NVM/flash.

```
$BDSUTC,10,00000000,0000000002000006,
$GALUTC,10,0O,14,00000081,32500000,328
```

UTC-модели BDS и Galileo из эфемерид (для конверсии GNSS-time в UTC).
Отображаются только когда они известны (bit «decoded from almanac»).
Не документированы публично, но формат полей соответствует ICD BDS и
Galileo.

```
$SVEPH_<NN>,<slot>,<hex>,<hex>,<hex>,...
```

Дамп эфемерид (SV ephemeris) по каждому отслеживаемому спутнику:
- `NN` — PRN / слот спутника в нашей системе нумерации (002, 011,
  013, 018, 020, 024, 072, 088, 115, 161, 167, 168 и т.д.),
- `slot` — индекс внутри constellation-таблицы (13, 17, 18, 180…),
- далее hex-данные эфемерид (в прошивочном формате, не RTCM).

Для нашей сессии модуль восстановил эфемериды на ≈16 спутников до
начала штатной работы.

### 4.2 Когда начинается рабочий поток

После ~6.7 КБ boot-dump и ~1.0 с после power-on включаются:
- штатный поток **NMEA**;
- потоки **RTCM3** (стандартный) и **Extended RTCM 4074** — если
  соответствующие `$CFGMSG` были сохранены в NVM через `$CFGSAVE`.

### 4.3 Обновление boot dump из нашей платы (`boot-capture`)

`src/unicore/boot_dump.bin` — байт-точная копия исходного потока с
живого чипа. Чтобы пересобрать его на новой прошивке/железе без
внешнего USB↔UART логгера, есть opt-in cargo-feature `boot-capture`,
который добавляет в Unicore-прошивку линейный one-shot RAM-буфер
`[u8; 8192]` на UART1 RX и периодически (каждые 10 с) выводит его
через `defmt-rtt`.

Сборка:

```bash
PATH="/home2/.cargo/bin:$PATH" cargo build --release \
    --features unicore,boot-capture --bin ublox_fake_uc
make flash
```

Захват:
1. Перевести плату в Passthrough (двойной клик кнопки).
2. Подключить реальный UC6580I на UART1 RX (GPIO5).
3. `probe-rs attach --chip RP235x … | tee /tmp/cap.log`, подождать
   30+ секунд (минимум 3 цикла дампа).

Условия freeze захвата (в `src/main_unicore.rs::uart1_rx_task`):
- буфер заполнен (8192 байта) **ИЛИ**
- 4 секунды от первого байта **ИЛИ**
- встретилась подстрока `$GNRMC` (начало steady-state).

Re-arm: тишина >500 мс на UART1 RX + новые байты → счётчик `EPOCH`
инкрементируется, буфер обнуляется. Покрывает повторные power-cycle
чипа без перезагрузки платы.

Декод RTT-лога:

```bash
python3 tools/decode_rtt_boot_capture.py \
    --input /tmp/cap.log \
    --out /tmp/new_boot_dump.bin \
    --diff src/unicore/boot_dump.bin
```

Скрипт парсит маркеры `==RAWCAP BEGIN epoch=N len=L crc=XXXX==` /
`==RAWCAP END==` и строки `RAWCAP <epoch> <off> <hex…>` (32 байта /
строка), реассемблирует словарём по offset, сверяет CRC32 (IEEE
802.3), при нескольких эпохах берёт последнюю полную. После
структурной валидации (`cargo test boot_dump` в `tests_host/` —
9 ассертов) копируем поверх `src/unicore/boot_dump.bin` и пересобираем
без `boot-capture`.

### 4.4 Mode 0 — Forced3dFix passthrough + coord override (2026-04-27 redesign)

**Старый hybrid Mode 0** (CFGKEY-trigger override + `emulation_task` со
своим NMEA-стримом) **снят**. Не работал — дрон детектировал смену
источника на switch'е и отваливался. История в git `1f6501c..7d9bc1f`.
Эта секция описывает текущую реализацию.

**Стратегия** (по предложению из старого TODO): Mode 0 = **Mode 4
(PassthroughOffset) + принудительный 3D fix + 22-секундное окно**. Все
chip-потоки идут as-is, переписываются только координатные NMEA, и
принудительно поднимается `fq=3` чтобы (теоретически) дать дрону отбить
home point.

**Что делает плата в Mode 0:**

| Поток | Что | Где |
|---|---|---|
| `$GxGGA / RMC / GSA / GLL` | подмена `force_3d_fix_sentence`: `lat/lon/alt = config::offset_target`, `fq=3`, `nsats=16`, `hdop=0.99`, `status=A`, `mode=A`, `fix_type=3` | `src/unicore/nmea.rs::force_3d_fix_sentence` |
| `$GxGSV / VTG / ZDA / TXT / $PNOISE / $P*` | verbatim passthrough | `process_nmea_line` final branch |
| RTCM3 (1005/1006/1077/1087/1097/1117/1127/1019/1046) | verbatim passthrough | RTCM router в `passthrough_forward_task` |
| ExtRTCM 4074 (sub-IDs 0x000–0x0FF, 0xE6/0xE9/0xF9/0xFE/0xFF…) | verbatim passthrough | то же |
| `$CFGKEY` etc. | по UART1 → UART0 (chip отвечает сам) | `uart1_rx_task` |

**Окно валидности** (`config::timers::SATELLITES_INVALID_AFTER_MS = 22_000` ms):

| Фаза | Что подменяется | LED |
|---|---|---|
| `0..22 s` после mode-entry | `fq=3, 16 sats, status=A, mode=A, fix_type=3` (`force_3d_fix_sentence`) | green |
| `≥ 22 s` | `fq=0, 1 sat, status=V, mode=N, fix_type=1` (`force_no_fix_sentence`) — координаты остаются target | yellow (`SATELLITES_INVALID=true`) |

Тайминг — атомик `FORCED3D_PHASE_START_MS: AtomicU32`. Армится при
cold-boot если persisted mode = Emulation, и при mode-change INTO
Emulation. Lazy-инициализация на первом фрейме если cold-boot прошёл с
`start=0`.

**Разрешение пустых полей чипа.** UC6580I в холодном старте шлёт
`$GNGGA,,,,,,0,...` и `$GNRMC,,V,,,,,,,,,,N,V*37` — поля time/date
пустые. Старая `force_*` отказывала и валилась в verbatim → дрон видел
чиповую `fq=0`. Новая `force_*` принимает `fallback_time` /
`fallback_date`:

- `fallback_time`: `NmeaTimeCache.last_time` (обновляется на любой
  checksum-ok GGA/RMC с непустым time, TTL 60 с) → если протух,
  `NmeaTime::default()` = `00:00:00.00`.
- `fallback_date`: `NmeaTimeCache.date` (TTL 1500 ms) → если протух,
  `NmeaDate { day:1, month:1, year:2025 }`.

Только bad-checksum или неизвестный sentence kind теперь возвращают
`None`. Verbatim-утечка координат чипа невозможна.

**Регрессионные тесты** (`tests_host/tests/test_unicore_nmea.rs`):
- `force_3d_gga_uses_target_fix_and_live_time`
- `force_3d_rmc_preserves_live_time_date_and_sets_valid_mode`
- `force_3d_gsa_preserves_talker_system_and_prns`
- `force_3d_gll_rewrites_target_and_status` — новый
- `force_3d_rejects_bad_checksum_only` — bad-checksum/unknown ⇒ `None`,

Все 239 хост-тестов зелёные.

### 4.5 Диагностика утечек координат под спуфом (`tx-trace`)

Cargo-feature `tx-trace` добавляет одну `info!()` строку перед **каждым**
`enqueue()` к UART0 TX (к дрону) когда `SPOOF_DETECTED == true`. Цель —
проверить что под спуфом ни один путь к дрону не несёт raw spoofed
координаты.

Категории в RTT (тег после `[TX→DRONE/]`):
- `spoof-rebuild-gga` / `-rmc` — наша подмена с LAST_GOOD (Phase-1) +
  `fq=0` / `mode=V`. Норма.
- `nmea-passthrough` — non-GGA/RMC verbatim. Должно содержать только
  `$GxGSA / $GxGSV / $GxTXT / $PNOISE / $PPSInfo` (без позиции).
- `rtcm-flush` — RTCM3 / ExtRTCM 4074 frame. Стандартные 1019/1077/1097/
  1046/1013 не несут receiver-position; ExtRTCM 4074 sub-IDs (0x000–
  0x0FF) — проприетарные status; ни в одном не должно быть Phase-2.
- `nmea-drop-spoof` / `nmea-drop-offset` — отброшенные GLL/VTG (норма
  под спуф / offset).
- `inter-sentence` — байты между sentence'ами (`\r\n` + мусор).

**Регрессионный замер 2026-04-26** (Air 3S + UC6580I, RF-спуф Phase-1
Montana → Phase-2 SPB):

| Категория | Количество | Содержат Phase-2? |
|---|---|---|
| spoof-rebuild-gga | 227 | нет, все Phase-1 + 75 m дрейф |
| spoof-rebuild-rmc | 226 | нет, все Phase-1 + 75 m дрейф |
| nmea-passthrough | 788 | нет ($GNTXT/GSA/GSV/PNOISE/PPSInfo) |
| rtcm-flush | 1929 | нет (1019/1077/4074 sub-IDs) |
| inter-sentence | 229 | нет (CRLF/мусор) |

Поиск Phase-2 байт-сигнатур в TX:
- ASCII (`,5956.`, `,03019.`, `,E,`, `59.94`, `30.33`) — **0 совпадений**
- int32 LE/BE для lat=599435895 (`23 B5 8E 37` / `37 8E B5 23`) и
  lon=303316483 (`12 15 0F 03` / `03 0F 15 12`) — **0 совпадений**
- f64 BE/LE — **0 совпадений**

**Вывод:** через нашу плату Phase-2 координаты к дрону не уходят.
Защита GGA/RMC rebuild + GLL/VTG drop полностью покрывает все
наблюдаемые UC6580I выходы. Если пилот видит на пульте spoofed
координаты — источник вне нашей платы (собственный GPS-приёмник дрона,
sensor fusion с IMU/vision, или external aiding через RTK base/A-GPS).

Production-сборка без флага: LTO-deads весь trace код, накладных нет.

### 4.6 Переключение режима платы через debug mailbox

В Unicore-прошивке есть отладочный mailbox в RAM:
`DEBUG_MODE_REQUEST: AtomicU8`. Idle value — `0xFF`; команда — enum
значение режима:

| Request | Режим | Эквивалент кнопки |
|---:|---|---:|
| `0` | `Emulation` | 1 клик |
| `1` | `Passthrough` | 2 клика |
| `2` | `PassthroughRaw` | 3 клика |
| `3` | `PassthroughOffset` | 4 клика |

Host-side утилита:

```bash
tools/debug_set_unicore_mode.py --mode emulation
tools/debug_set_unicore_mode.py --mode passthrough
tools/debug_set_unicore_mode.py --mode raw
tools/debug_set_unicore_mode.py --mode offset
```

Скрипт не хардкодит адреса: он ищет `DEBUG_MODE_REQUEST` и `MODE` в
ELF через `nm`, пишет один байт через `probe-rs write --chip RP2350 b8`,
затем читает `MODE` до подтверждения фактического runtime state.

Применение выполняет сама прошивка: задача `debug_mode_request_task`
делает `swap(0xFF)`, валидирует `0..=3` и вызывает тот же helper, что
и `button_task`. Поэтому debug-переключение сбрасывает spoof/emulation
state, ставит `SPOOF_DETECTOR_RESET` и сохраняет режим во flash. Прямой
poke в `MODE` использовать нельзя как основной путь: он меняет только
runtime byte и обходит reset/save side effects.

Проверенный быстрый сценарий:

```bash
cargo build --release --features "rp2350 unicore" \
    --bin ublox_fake_uc --target thumbv8m.main-none-eabihf
probe-rs download --chip RP2350 --verify \
    target/thumbv8m.main-none-eabihf/release/ublox_fake_uc
tools/debug_set_unicore_mode.py --mode passthrough
tools/debug_set_unicore_mode.py --mode offset
probe-rs reset --chip RP2350
MODE_ADDR=$(nm --defined-only target/thumbv8m.main-none-eabihf/release/ublox_fake_uc \
    | awk '$NF=="MODE"{print "0x"$1}')
probe-rs read --chip RP2350 b8 "$MODE_ADDR" 1
```

После reset должен читаться последний сохранённый режим (`03` для
`PassthroughOffset`). Для RP2354 используйте `--chip RP2354` или
соответствующий `probe-rs` preset.

## 5. Командный протокол

### 5.1 Формат командной строки (doc 2.1)

```
$<CMD>[,<arg>,<arg>,...][*cs]<CR><LF>
```

- `$` — SOF, 0x24.
- `<CMD>` — ASCII мнемоника.
- Аргументы через запятую. Hex-значения записываются в форме
  `h<hex>` или `H<hex>` (пример: `h55155`).
- Чек-сумма `*cs` — **опциональна** (см. раздел FAIL ниже):
  модуль принимает команды без `*HH`. В доке указано «в модели
  ответа используется XOR всех байт между `$` и `*`».
- Конец строки: `\r\n`.

### 5.2 Ответы (doc 3.2.3 / 3.2.4)

Модель ответа Unicore очень простая:

```
$OK*cs                — команда принята и выполнена, cs = 04 (XOR "OK")
$FAIL,errorCode*cs    — команда отвергнута
  errorCode = 0  → неверные параметры
  errorCode = 1  → неверная чек-сумма
```

Ответ на **GET**-форму (команда без rate/value) дополнительно содержит
строку ответа вида `$<CMD>,<current-value>*cs` перед `$OK*04`.

**Дополнительно** наблюдается проприетарный ACK через `$GNTXT`:

```
$GNTXT,nn,nn,id,<echoed-command-body>*cs
```

`id` здесь — severity:
- `00` — информативное (в логах — эхо параметров команды для «set»),
- `03` — Ephemeris Lacking (doc 3.5.4),
- `04` — Data Incomplete (doc 3.5.5).

Это **не замена** `$OK*04`, а дополнительное подтверждение.

| bit 14 | Galileo E5a |
| bit 16 | QZSS L1 C/A |
| bit 18 | QZSS L5 |

Итого: **GPS L1+L5 · BDS B1I+B2a · GLONASS L1 · Galileo E1+E5a ·
QZSS L1+L5** — full-constellation dual-band без SBAS и NavIC. Совпадает с
заявленным `G1B1L1E1` в `$PDTINFO` (флаги там — только «L1 поддерживается»,
L5 приходит из маски).

⚠️ **После SET команда вызывает автоматический reset**. Поэтому
`$CFGSYS,h...` нельзя вызывать в середине работы — только при
инициализации.

### 5.6 `$CFGNAV` — частота навигации (doc 3.3.6)

```
$CFGNAV,MeasRate,NavRate,DRNavRate
```

- `MeasRate` — интервал наблюдений (мс): 1000 = 1 Гц, 200 = 5 Гц,
  100 = 10 Гц.
- `NavRate` — интервал навигационного решения (мс).
- `DRNavRate` — интервал INS (только для integrated).

`MeasRate == NavRate` обязательно. В наших логах не опрашивался, но
косвенно `NavRate = 200` (5 Гц), т.к. все NMEA идут на 5 Гц.

### 5.7 `$CFGSAVE` и `$CFGCLR` (doc 3.3.23 / 3.3.24)

```
$CFGSAVE  — сохранить текущую конфигурацию в flash
$CFGCLR   — очистить пользовательскую конфигурацию (эффект после reset)
```

⚠️ Не выключать питание в течение 1 с после `$CFGSAVE` — иначе flash
может быть повреждён и настройки сбросятся в factory defaults.

### 5.8 `$CFGKEY` — authorization code (не в публичной R1.2)

В публичной R1.2 команды `$CFGKEY` **нет**. В нашем логе она работает:

```
GET:  $CFGKEY
OUT:  $CFGKEY,,6adae970f433a1c9c55f3bd7092b1400f40dddc4c715c39a5aed529158f001
              01010101010101010101010101010101010101,D0645C*3B
```

#### Тайминг — критично для захвата

`$CFGKEY` приходит от дрона **последней** в стандартном handshake — через
**~19.3 секунды** после первого `$PDTINFO`. Чип отвечает за ~9 ms.

Эталон из живого DSLogic-захвата (`logs_analiser/2026-04-26_165030_neo_asc2.txt`):
- `16:51:09:842` — drone → chip: первый `$PDTINFO`
- (далее `$CFGMSG×4`, `$CFGSAVE`, `$CFGSYS×2`)
- `16:51:29:109` — drone → chip: `$CFGKEY` ← **+19.27 сек**
- `16:51:29:100` — chip → drone: `$CFGKEY,,<160-hex>,<CRC24>` (опережает на 9 ms — drone-side timestamp пишется чуть позже из-за UART buffering)

Подтверждено on-board capture'ом (`/tmp/cap.log`, 2026-04-26 17:35):
`boot-capture frozen [DRONE]: epoch=0 len=118 elapsed_ms=19761` — drone-side
буфер замёрз через 19.76 секунд по `$CFGKEY` sentinel.

⚠️ Чтобы попасть на `$CFGKEY` через `boot-capture`/`tx-trace`/sniffer:
- держать `probe-rs attach` подключенным **минимум 25 сек после
  power-on дрона** (наш `FREEZE_AFTER_MS_DR = 25_000` ms);
- если делаешь захват DSLogic'ом — записывать ≥ 30 секунд от первого
  байта.

Формат: `$CFGKEY,<slot>,<160-hex-chars>,<CRC24-hex>*cs`.

- `<slot>` — в нашей сессии пустой. В многослотовых прошивках
  возможно указание номера слота.
- Ключ — ровно 80 байт (160 hex-символов). Концевые
  `0101010101...01` — padding (18 байт `0x01`, слот фиксированного
  размера не заполнен полностью).
- `CRC24-hex` — 6 hex-символов (`D0645C` в нашем случае), CRC24-Q
  (полином `0x1864CFB`).
- `*cs` — стандартная NMEA-XOR.

**Функциональное назначение** (по аналогии с `CONFIG AUTHCODE` в
линейке высокоточных приёмников N4: UM980 / UM960 / UM982, см.
[N4 Reference Commands Manual R1.4 §4.26](https://en.unicore.com/uploads/file/Unicore%20Reference%20Commands%20Manual%20For%20N4%20High%20Precision%20Products_V2_EN_R1.4.pdf)):

> «This command is used to add authorization code for the receiver.
> Once the correct code is entered, the receiver will automatically
> save the authorization information and restart. The saved
> information cannot be erased by updating firmware or using FRESET
> command. Entering a wrong code will make the receiver work
> abnormally.»

В N4 AUTHCODE — длинная строка вида
`0x000000bf:080101007502:<PN>:<exp>:<type>:<ECDSA-signature>`
(поля разделены `:`), в UFirebird II её эквивалент — компактный
80-байтовый blob в `$CFGKEY`. Общее назначение одинаково:

- Активирует набор featur'ов: сигналы / созвездия (`$CFGSYS`),
  частоту `NavRate`, RTCM-сообщения (включая proprietary **4074**),
  режимы работы.
- Привязан к конкретному чипу (через SN/PN), подписан криптографически.
- Хранится в защищённой области flash, **не стирается** ни
  `$CFGCLR`, ни апдейтом прошивки.

#### Нужно ли его записывать?

**Нет, не нужно.** Чип приходит с завода с уже установленным ключом
(GET возвращает валидный blob с корректным CRC). Весь наблюдаемый
функционал (L1+L5, MSM7 по всем созвездиям, extended RTCM 4074) уже
включён. Заводской ключ перекрывает все featur'ы нашей прошивки
`R6.1.1.1Build9074`.

Практическая роль `$CFGKEY`:

1. **Чтение (GET)** — безопасно, позволяет снять бэкап ключа на
   случай повреждения flash или ремонта. Рекомендуется записать
   в проект при получении новой партии чипов.
2. **Запись (SET)** — только при получении нового ключа от Unicore
   (например, при расширении лицензии через NDA) или для
   восстановления после сбоя.

⚠️ **Запись ключа опасна**. По аналогии с N4 AUTHCODE: «entering a
wrong code will make the receiver work abnormally», и результат
**неустраним** ни `$CFGCLR`, ни firmware upgrade. SET-форма в
наших логах не проверена. Без резервной копии оригинала —
не экспериментировать.

### 6.2 Standard RTCM3

Включается через `$CFGMSG,2,<id>,<rate>`. В нашей сессии:

| Msg ID | Кол-во | Частота | Что это |
|---|---|---|---|
| **1077** | 658 | **4.96 Гц** | GPS MSM7 (code, phase, Doppler, CN0 по L1/L2/L5) |

MSM-тип (1074/1075/1076/1077) определяется через `$CFGMSM,MsmType`:

### 6.3 Extended RTCM (Unicore proprietary msg 4074)

Формат — стандартный RTCM3 фрейм (`0xD3` preamble + 10-bit length
+ payload + CRC24-Q), но **Message Type = 4074** (зарезервированный
диапазон 4001–4095 для вендоров).

Структура payload (Table 5-3):

```
┌──────────┬──────────┬────────────────┬──────────┐
│ MsgType  │ SubMsgID │   Data field   │  CRC24Q  │
│  12 bit  │  12 bit  │     N байт     │  24 bit  │
│  = 4074  │          │                │          │
└──────────┴──────────┴────────────────┴──────────┘
 (поверх стандартного header D3+len)
```

Все проприетарные сообщения кодируются **Big Endian**.

**Наблюдаемые Sub-ID в нашей сессии** (2032 кадра 4074):

| Sub-ID (hex) | Кол-во | L (payload) | Частота | Doc Sec | Описание |
|---|---|---|---|---|---|
| 0x0FE | 626 | 14 | 4.72 Гц | 5.2.2.2 | **Signal Information** |
| 0x0E6 | 623 | 31 | 4.70 Гц | 5.2.2.9 | **Hardware Status** (доп.: в доке указано «1 Hz», но реально выдаётся ~5 Гц — возможно это отличие R6.1) |
| 0x0F9 | 440 | 57 | 3.32 Гц | 5.2.2.5 | **Protection Level Information** |
| 0x0E9 | 132 | 18 | 1.00 Гц | 5.2.2.7 | **Jamming and Spoofing Detection** |
| 0x0FF | 13 | 163 | 0.10 Гц | 5.2.2.1 | **Receiver Information** |
| 0x0FC | 10 | 133 | 0.08 Гц | — | **не в R1.2** (возможно Protocol/Firmware Info) |
| 0x000 | 91 | 5 | 0.69 Гц | — | **не в R1.2** (очень короткий, 5 байт) |
| 0x001 | 95 | 3 | 0.72 Гц | — | **не в R1.2** (3 байта = только header без data) |
| 0x002 | 2 | 48 | 0.02 Гц | — | **не в R1.2** |

Все остальные Sub-ID из Table 5-3 (TGD 0xFD, Ionosphere 0xFB,
Leap 0xEA, SBAS 0xE8, PPS 0xE4, sensor-fusion 0x00B…0x014) в нашей
сессии **не выдаются** — не запрошены конфигурацией.

#### 5.3.1 Sub 0x0FF — Receiver Information

payload = 163 байта. Из Table 5-X документа это **большой status-пакет**
с полем `quality` (обновлённым в R1.2), версиями, временем, PVT-состоянием.
Точный layout — см. doc 5.2.2.1.

#### 5.3.2 Sub 0x0FE — Signal Information

payload = 14 байт. Короткий пакет — CN0 + carrier info по отслеживаемым
каналам.

#### 5.3.3 Sub 0x0F9 — Protection Level

payload = 57 байт. HPL/VPL/TPL (Horizontal/Vertical/Time Protection Level)
для функциональной безопасности / integrity monitoring.

#### 5.3.4 Sub 0x0E9 — Jamming & Spoofing Detection

payload = 18 байт. Флаги обнаружения помех и спуфинга (R1.2 раздел
5.2.2.7).

#### 5.3.5 Sub 0x0E6 — Hardware Status

payload = 31 байт. Температура, уровни питания, AGC. См. 5.2.2.9.

## 7. Типичный скрипт инициализации

Наблюдён в raw-логе ttyUSB1:

```
$PDTINFO\r\n              → проверить модель/прошивку/SN
$CFGMSG,9,12,1\r\n        → bundle status-пакетов (Signal/Protection/Jam/Rcv/HW)
$CFGMSG,9,12\r\n          → подтвердить
$CFGMSG,9,15,1\r\n        → Hardware Status (Sub 0xE6)
$CFGMSG,9,15\r\n          → подтвердить
$CFGSAVE\r\n              → записать в flash
$CFGSYS\r\n               → прочитать маску созвездий
$CFGSYS\r\n               (дубль)
$CFGSYS\r\n               (дубль)
$CFGKEY\r\n               → прочитать лицензию
```

*За всю сессию 132 с хост больше ничего не шлёт.* Конфигурация
применяется только один раз; дальше модуль работает автономно
согласно NVM.

Для изменения конфигурации в своём сценарии:

```
$CFGNAV,200,200,0\r\n          # 5 Hz nav
$CFGSYS,h55155\r\n             # L1+L5 dual-band
                                # (модуль ресетится!)
$CFGMSG,0,0,1\r\n              # GGA at NavRate
$CFGMSG,0,4,1\r\n              # RMC at NavRate
$CFGMSG,0,2,1\r\n              # GSA at NavRate
$CFGMSG,0,3,5\r\n              # GSV at 1 Hz
$CFGMSG,2,3,1\r\n              # RTCM MSM
$CFGMSG,2,4,1\r\n              # RTCM Ephemeris
$CFGMSG,9,15,1\r\n             # HW Status
$CFGSAVE\r\n                   # в flash
```

## 8. Практические замечания по парсингу

1. **Смешанный поток NMEA + RTCM3 + Extended RTCM**. Любой
   парсер, режущий поток по `$`, обязан уметь пропускать RTCM-кадры
   (начинаются с `0xD3`), иначе случайные `0x24` внутри RTCM-payload
   будут раскалывать NMEA на мусор. См. артефакты в `uart_term` с
   тэгами типа `GNG0000`, `G3`, `GN19`.

2. **Делимитерное разбиение на `B5 62` не подходит** — это UBX
   (u-blox), у Unicore таких маркеров нет. Единственный корректный
   режим для `uart_term` — **raw, без делимитера**, с внешним разбором
   по трём форматам (NMEA, RTCM3, Extended RTCM 4074).

3. **CRC24-Q обязательна** для валидации RTCM-кадров; полином
   `0x1864CFB`, начальное значение 0. Проверять над `header+payload`,
   сравнивать с последними 3 байтами кадра.

4. **Boot-dump занимает до 2.3 КБ**. На 115 200 бод это ≈200 мс.
   Если логгер подключается позже — часть диагностики теряется.

5. **`$CFGSYS,h...` триггерит reset**. После set-команды нужно
   дать модулю ~1 с прогреться и заново прочитать boot-dump.

6. **Недокументированные поля** (`$CFGKEY`, `$PNOISE`,
   `$CHCFG`, `$PTINFOPKG`, `$SVEPH_*`, sub-ID `0x000 / 0x001 /
   0x002 / 0x0FC` в 4074) — встречаются в прошивке
   R6.1.1.1Build9074, но отсутствуют в публичной доке R1.2.
   Для конкретной интерпретации нужен OEM-ICD от Unicore
   (через NDA).

## 9. Что осталось открытым

- Точное значение `$CFGMSG,9,12` — в публичной R1.2 нет.
  Рабочая гипотеза: bundle «all status extended messages». Нужно
  подтвердить экспериментом (послать «0» для выключения и смотреть,
  какие sub-ID пропадут).
- Sub-ID `0x000 / 0x001 / 0x002 / 0x0FC` в msg 4074 — неизвестны.
  Для sub=0x001 payload всего 3 байта (только header без data) —
  может быть keep-alive или counter.
- Формат `$CHCFG`, `$PTINFOPKG`, `$SVEPH_*` — на 80 % совпадает
  с полями RTCM Ephemeris (1019/1042/1046), можно сверить и
  восстановить.
- Семантика полей 1–2 и 11–12 в `$PNOISE`.
- Response-checksum `$GNTXT,01,01,<id>,...` — для кодов `id`
  `03/04` есть doc (Ephemeris Lacking / Data Incomplete), `00` —
  общий ACK; остальных не видели.

механизм. Функциональное назначение неизвестно.

Семантика выдачи pre-ACK `$GNTXT,01,01,00,<CMD>*cs`:
- **Есть** для: `$CFGSYS`, `$CFGNAV`, `$CFGPRT`, и всех `$CFGMSG`.
- **Нет** для: `$PDTINFO`, `$PRODUCTINFO`, `$CFGKEY`, `$CFGNMEA`.

### Семантика ошибок

| Случай | Ответ чипа |
|--------|-----------|
| Unknown CMD name (`$XYZ,...`) | **молчание** (ни `$OK`, ни `$FAIL`) |
| Known CMD, malformed args (`$CFGMSG,x,12`) | `$GNTXT,01,01,00,<body>*cs` + `$FAIL,0*1E` |
| Known CMD, extra args (`$PDTINFO,extra`) | `$GNTXT,...` + `$FAIL,0` |
| Known CMD, unknown (class,id) (`$CFGMSG,99,0,1`) | `$GNTXT,...` + `$FAIL,0` |
| Known CMD, bad XOR (`$CFGSYS*00`) | `$GNTXT,01,01,00,<body*00>*cs` + `$FAIL,1*1F` (с невалидной `*XX` в echo!) |

### Port config (`$CFGPRT,1` GET)

```
$CFGPRT,1,0,921600,H81,H12F*79
```

- `portID=1` — UART1
- `addr=0`
- `baud=921600`
- `inPro=0x81` = bits 0 (UNICORE) + 7 (RTCM3.3 input)
- `outPro=0x12F` = bits 0,1,2,3,5,8 (UNICORE output + NMEA + RTCM3.3 +
  bit3 unknown + Notice + Ext-RTCM 4074 PVT)

Значение bit3 в `outPro` в публичной R1.2 не описано.

`$CFGPRT,2` (UART2) даёт `$CFGPRT,2,0,921600,H1,H0*37` — тот же baud, но
`inPro=0x01` (только UNICORE input) и `outPro=0x00` (ничего не выводится).
`$CFGPRT,0` и `$CFGPRT,4` → `$FAIL,0` на UC6580I.

### Прочие GET-команды

| Команда | Ответ (live 2026-04-23) | Примечание |
|---------|-------------------------|------------|
| `$CFGMSM` | `$CFGMSM,7,0*16` | MSM type = 7 (MSM7). Второе поле undoc |
| `$CFGNMEA` | `$CFGNMEA,H52*26` | NMEA-флаги/версия, точная семантика в R1.2 не раскрыта |

Classes `$CFGMSG,4/5/6/7/8,*` — **не поддерживаются на UC6580I** (чип
возвращает `$FAIL,0`, доступны только на UM621/UM681A по doc Table 3-12).

### Дополнительные сообщения в steady state с fix

После установления 3D fix на чипе идут сообщения, отсутствующие в холодном
логе 2026-04-22:

| Сообщение | Частота | Назначение (эмпирически) |
|-----------|---------|--------------------------|
| RTCM **1013** | ~1 Гц | System Parameters (состав созвездий/эпоха) |
| `$CWOUT,<fields>*cs` | ~1 Гц | AGC / CW-интерференция (не в доке R1.2) |
| `$GNGLL`, `$GNVTG`, `$GNZDA`, `$GNGST`, `$GNGBS` | при `$CFGMSG,0,<id>,1` | NMEA дополнительные |
| `$SVEPH_<PRN>` | event-driven | свежая эфемерида SV |
| `$PPSInfo:...` | ~0.06 Гц (раз в 15+ с) | 1PPS status/config |

Пример `$CWOUT`: `$CWOUT,1,0,0,0,0,0,0,1169998,-113*6E`.

### Что наш эмулятор воспроизводит 1:1 (all bit-exact verified)

- `$PDTINFO` / `$PRODUCTINFO` / `$CFGSYS,H55155` / `$CFGNAV,200,200,0` /
  `$CFGKEY,...*3B` — точные байты ответа чипа.
- Pre-ACK `$GNTXT` с корректной XOR-чек-суммой для `$CFGSYS`, `$CFGNAV`,
  `$CFGMSG`.
- `$FAIL,0` / `$FAIL,1` в тех же случаях, что и чип.
- RTCM 1077, 1019, 1046, 1097, **1013** — byte-for-byte из наших captures.
- ExtRTCM 4074 Sub-IDs: 0x0FE, 0x0FF, 0x0F9, 0x0FC, 0x0E9, 0x0E6, 0x000,
  0x001, 0x002 — все данные захвачены на живом чипе.
- `$CWOUT`, `$SVEPH_*`, `$PPSInfo:...` — захваченные реальные строки.
- Silent на Unknown CMD, `$GNTXT` echo на BadCS / Malformed.

## 9-ter. Spoof-detection flow (UC6580I emulator)

Алгоритм полностью идентичен u-blox ветке (`src/main.rs::gnss_processing_task`
NAV-PVT ветка). Отличается только протокол — UBX → NMEA.

**Mapping UBX → NMEA для detector:**

| u-blox вход | UC6580I эквивалент |
|-------------|--------------------|
| `NAV-PVT` (0x01 0x07) запускает detector | `$GNGGA` запускает detector |
| `NAV-POSLLH` (0x01 0x02) — дубль координат | `$GNRMC` — дубль координат |
| `PositionBuffer` (15 entries, 3 с) | идентичный `PositionBuffer` inlined |
| `DynamicOffset` once-and-forever | идентичный `DynamicOffset` |

**Спуф-цикл:**

1. **Normal fix**: `SpoofDetector::analyze` ⇒ `AnalysisResult::Normal`. Координаты пушатся в `PositionBuffer` (только при валидном 3D fix).
2. **Edge Normal→Spoofed**: берётся позиция `PositionBuffer::get_position_at(2, now_ms)` — **2 с до** события. Сохраняется в `LAST_GOOD_*`. `SPOOF_DETECTED = true`. `SPOOF_RECOVERY_START_MS = 0`.
3. **Spoofed продолжается**: `SPOOF_RECOVERY_START_MS = 0` (сбрасывает незавершённый recovery).
4. **Edge Spoofed→Normal**: `SPOOF_RECOVERY_START_MS = now_ms`. `SPOOF_DETECTED` ещё `true`.
5. **Normal длится**: если `now_ms - start ≥ 5000` → `SPOOF_DETECTED = false`, таймер сброс. **DynamicOffset не трогается**.

**Смена режима** через кнопку или debug mailbox ⇒ `SPOOF_DETECTOR_RESET` ⇒ в `passthrough_forward_task` сбрасывается detector + PositionBuffer + dynamic_offset + SPOOF_* flags + LineAssembler.

**Модификация выхода под спуф** (аналог `modify_nav_pvt_spoof`):

| u-blox | UC6580I | Значение под spoof |
|---|---|---|
| NAV-PVT lat/lon/alt | `$GNGGA`/`$GNRMC` lat/lon/alt | `LAST_GOOD_*` (+ offset в Mode 4) |
| fix_type | GGA fix_quality | `0` |
| num_sv | GGA nsats | `1` (один видимый, но невалидный спутник) |
| velN/E/D | RMC sog_knots, cog_deg | `0`, `0` |
| flags | RMC status / mode | `V` / `N` |

**PassthroughOffset + offset не вычислен:** GGA/RMC **suppressed** (аналог `match id { 0x07|0x02|0x01|0x13|0x06 => continue }` в u-blox), чтобы не утекла реальная позиция.
